# ADR 0012: ローカルの Airflow には、ロールの一時キーだけを渡す

- 日付: 2026-11-07
- 状態: 採用(実装は、フェーズ2の「Airflow の土台」で行う)
- 関係: ADR 0007(ローカルの Docker で動かす Airflow)の未決を、この ADR で決める。secrets.md の一覧も更新する

## 状況

Airflow は Docker のコンテナで動き、ingest ロール(Raw の読み書き)と transform ロール(dbt)を借りる必要がある。手元では、portfolio-admin の長期の鍵(`~/.aws`)からロールを借りている。この鍵は強い権限を持つので、コンテナには入れない(ADR 0007)。

## 決めたこと

- **コンテナには、ロールの一時キーだけを渡す。** 手元(Mac)で管理者がロールを借り、期限付きの一時キーを、1つのファイルに書き出す。
- **プロファイルの名前は、いまと同じにする。** ファイルの中は `ecom-dev-ingest` と `ecom-dev-transform` の2つ。コンテナの中でも `AWS_PROFILE` で切り替わるので、ingestion と dbt のコードは変えない。
- **ファイルは、読み取り専用でコンテナに見せる(マウント)。** 置き場所は Git の管理外にする。書き出しの手順はスクリプトにまとめる。
- **期限は、まずロールの既定(1時間)のまま使う。** Airflow を使う前に、ユーザーが発行し直す。

## 理由

- 漏れたときの被害が小さい。一時キーは1時間で使えなくなり、できることも2つのロールの範囲に限られる。
- AWS の中や CI での「鍵を持たない形」(ロールを借りる、OIDC)と、同じ考え方になる。secrets.md の方針「鍵を持たない形を第一にする」に合う。
- 新しい IAM ユーザーや認証局が要らない。AWS の変更なしで始められる。

## 比べた案

- **Airflow 専用の IAM ユーザー(ロールを借りる権限だけ):** 発行し直す手間はないが、長期の鍵がコンテナに入る。
- **IAM Roles Anywhere(証明書で借りる):** 長期の鍵はどこにもないが、認証局と証明書の準備が重く、フェーズ2の学習の範囲から外れる。
- **`~/.aws` をそのままマウントする:** 管理者の長期の鍵がコンテナに入るので、採らない。

## あきらめたこと(弱い点)

- Airflow を使う前に、毎回、発行のコマンドを打つ必要がある。期限が切れると、タスクは認証エラーで失敗する。
- 1時間を超える処理(全期間のバックフィルなど)は、途中で期限が切れることがある。そのときの対応(ロールの最長の時間を Terraform で延ばす、窓を分けて発行し直す)は、バックフィルのタスクで決める。
