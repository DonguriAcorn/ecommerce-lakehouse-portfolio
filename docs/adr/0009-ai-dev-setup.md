# ADR 0009: AI 開発の構成は、止める・守る・手順・批評の4つに分けて置く

- 日付: 2026-11-03
- 状態: 採用(あとで入れるものは tasks.md にある)

## 状況

Claude Code を使って開発する。リポジトリは Public で、AWS を実際に変えられる権限が手元にある。誤って秘密を上げたり、AWS を変えたりしないこと、そして初学者が1ステップずつ理解して進めることが必要である。

## 決めたこと

守りたい強さごとに、置き場所を分けた。

| 内容 | 置き場所 | 例 |
|---|---|---|
| 絶対に止めること | `.claude/settings.json` の deny と、`.claude/hooks/guard-bash.sh` | 秘密のファイル、`git add .`、`terraform apply` / `destroy`、状態ファイルの中身を出すコマンド |
| いつも守ること | `CLAUDE.md` | 1ステップずつ進める、1行ずつ説明する |
| ときどきやる手順 | `.claude/skills/` | session-start、session-end、tf-plan |
| 大きな方針の批評 | `.claude/agents/plan-critic.md` | フェーズの計画、データが消える恐れのある作業の前に3回 |

- 最後の守りは、コミットの前の gitleaks にする。
- 入れないもの: AWS API の MCP(AWS を変えるのはユーザー)、GitHub の MCP、コードレビューやセキュリティの専用サブエージェント(組み込みの `/code-review` と `/security-review` で足りる)、テストを書くサブエージェント(ユーザーが書く方針)、plugins、Sandbox(様子見)。

## 理由

- 守りの強さに合わせた置き場所にすれば、重要なものほど確実に効く。`CLAUDE.md` は「読んで守る」もので、止める力がない。止めるべきものは、設定と hook に置く。
- `terraform apply` をユーザーだけが打つ形にすると、AWS を変える操作を人が必ず確認できる。
- plan-critic に3回レビューさせると、モジュール化のような大きな作業の穴が事前に見つかる(2026-11-03 のモジュール化で、手順 0 の追加、`moved` の置き場所、`tfplan` の除外などが見つかった)。

## あきらめたこと(弱い点)

- deny は文字列の照合なので、完全ではない。回避される可能性がある。
- hook が強いため、安全な確認も止まることがある。2026-11-03 には、`terraform state list` と `terraform show` が止まり、代わりに plan の出力を数えた。必要なら、ユーザーがターミナルで打つ。
- plan-critic は、1体の観点で見る。偏りがないかは、使いながら確かめる。
