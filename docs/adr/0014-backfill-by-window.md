# ADR 0014: バックフィルは期間の窓ごとに流し、全期間の流し直しはしない

- 日付: 2026-11-14
- 状態: 採用(同日に実装。30 日と 120 日の窓を流して成功)
- 関係: ADR 0007(ローカルの Airflow)、ADR 0012(一時キー)

## 状況

DAG `olist_daily` は1日しか流せない。過去分の流し直し(バックフィル)には、期間を渡せる形が要る。一時キーは 1 時間で切れる(ADR 0012)ので、長い処理は途中で止まる恐れがあった。ADR 0012 は、この対応を「バックフィルのタスクで決める」としていた。

実測(2016-09-04 の1日): 取り込み 約 3 秒、S3 へ 約 3 秒、dbt run 約 37 秒、dbt test 約 63 秒。1日ずつ 775 回流すと約 24 時間かかる。

## 決めたこと

1. 期間を渡せる DAG `olist_backfill`(`start_date` と `end_date`)を作る。窓ごとに、7表の取り込み → S3 → dbt run → dbt test を、それぞれ1回だけ流す。リトライは 0(期限切れは、待ってやり直しても直らないため)。
2. 一時キーの期限には、窓を分け、窓の前に手元で発行し直して対応する。ロールの最長時間は延ばさない(IAM を変えず、キーの寿命も短いまま)。
3. 全期間の流し直しはしない。データは Raw / Silver に全期間入っていて、Raw は上書き、Silver は MERGE なので、流し直しても中身は変わらない。

## 理由

- 実測では、窓を 4 倍にしても全体は約 1.4 倍にしかならなかった(30 日: 1 分 40 秒、120 日: 2 分 21 秒)。時間の大半は dbt で、窓の大きさにほとんど左右されない。増えるのは、取り込みと S3 へのアップロードだけ。
- そのため、1窓は 1 時間の期限に大きな余裕で収まり、窓の数を減らせる。

## 確かめたこと

- 30 日と 120 日の窓が、どちらも全タスク成功(dbt tests も PASS)。
- Silver 7表の行数とキーの種類の数が、元の CSV と一致(Athena で確認)。

## あきらめたこと(弱い点)

- データが多い時期(2018 年)の窓は、実測していない。立ち上がりの時期の数字からの外挿である。
- 流し直しの前後で、中身の指紋は比べていない。確認は、dbt tests の PASS と、行数・キーの種類の数の一致まで。
- 窓の前に、一時キーの発行をユーザーが手で打つ。窓の数が多いと手間が増える(窓が大きいほど少なくて済む)。
