# ADR 0013: Iceberg の整理(OPTIMIZE / VACUUM)は、手動の DAG で、7表を同じ形で流す

- 日付: 2026-11-14
- 状態: 採用(同日に実装。`orders_from_events` で効果と安全を確かめ、7表すべてを DAG で流して成功)
- 関係: ADR 0003(テーブル定義の管理)、ADR 0007(ローカルの Airflow)、ADR 0012(一時キー)。手順は docs/design/iceberg-maintenance.md

## 状況

Silver は Iceberg で、dbt の incremental + merge で、1日ぶんの窓ごとに書く。Iceberg はファイルを書き換えず、新しいファイルを作り、古いファイルは過去の版(スナップショット)から使われるうちは残す。そのため、`orders_from_events` は S3 に Parquet が 109 個(現在の版が使うのは 61 個)たまり、`record_count` の合計は実際の行数の約 2 倍(201,014 対 99,441)だった。何もしなければ、読むのが遅くなり、S3 の量も増え続ける。

## 決めたこと

- **整理は、OPTIMIZE(`REWRITE DATA USING BIN_PACK`)のあとに VACUUM を流す。** 順番は変えない(VACUUM が先だと、まとめる前のファイルを消せない)。
- **スナップショットは 7 日残す。** `vacuum_max_snapshot_age_seconds = 604800`。`vacuum_min_snapshots_to_keep` は既定の 1 のまま。
- **この設定は、整理のスクリプト(`ingestion/iceberg_maintenance.py`)が、毎回 `ALTER TABLE ... SET TBLPROPERTIES` で入れ直す。** 同じ値を何度入れても同じ(冪等)。
- **7表すべてに、同じ形で流す。** ファイルが 1〜2 個の表(いまは `orders_from_events` 以外)でも、場合分けしない。
- **Airflow の別の DAG(`iceberg_maintenance`)で、手動で実行する。** スケジュールは組まない。リトライは 0。1表の失敗で残りの表を止めず、最後に失敗した表をまとめて出し、タスクは失敗にする。
- **Athena の接続は boto3 で行う。** ロールは transform(dbt と同じ)。

## 理由

- 効果を確かめられた。`orders_from_events` の S3 の Parquet は 109 個から 25 個(約 77% 減)、現在の版の大きさは 12.9 MB から 6.5 MB になった。行数(99,441)と、業務の8列の指紋は、前後で同じ。
- 設定を、dbt のモデルの設定ではなくスクリプトに置くと、作成済みのテーブルにも確実に届く。dbt の incremental は、設定をテーブルを作るときにしか書かず、このプロジェクトは full-refresh をしない方針と合わない。
- 手動の DAG にすると、再現でき、ログも残る。ローカルの Airflow は一時キーが 1 時間で切れるので、定期実行は動かない(ADR 0012)。
- 7表を同じ形にすると、バックフィルのあとや、表が増えたときに、変更なしで効く。OPTIMIZE は、まとめるものがない表では何もしない。

## 比べた案

- **dbt のモデルの設定(`tblproperties`)に保存期間を入れる:** 設定が dbt に集まるが、作成済みのテーブルへは full-refresh が要る。
- **`olist_daily` の最後に足す:** 毎日自動で動くが、整理は毎日は要らない。整理が失敗すると、毎日の DAG が失敗に見える。
- **`orders_from_events` だけを整理する:** 簡単だが、バックフィルのあとに `order_items` や `reviews` を後から足す手間が出る。
- **保存期間を 3 日 / 14 日にする:** 3 日は、週末をはさむと直前の版に戻れないことがある。14 日は、古いファイルが残り、S3 のバージョニング(非現行の版を 14 日)と合わせて約 28 日残る。

## あきらめたこと(弱い点)

- 整理を忘れても、気づく仕組みはない。バックフィルのあとに流す、という運用で守る(手順書に書く)。
- VACUUM は、消した版に戻れない。7 日より古い版には、戻れない。
- 消したファイルは、S3 のバージョニングで、非現行の版として 14 日残る。S3 の料金が下がるのは、約 14 日後。
- 整理が、`olist_daily`(MERGE)と重なると、書き込みが衝突することがある。重ねない運用で守っていて、DAG が重なりを防ぐ仕組みは入れていない。
- 新しいテーブルを足したときは、`TABLES` の一覧に 1 件足す必要がある。
