# ADR 0004: Raw は日付ごとのスナップショットの Parquet にし、型は Raw の段階で付ける

- 日付: 2026-11-03(決めたのは 2026-10-22〜25。詳細は docs/design/orders-vertical-slice.md)
- 状態: 採用(orders のみ実装。他のテーブルはフェーズ2で広げる)

## 状況

Olist の元データは、最終的な状態の CSV 1回分である。日次の取り込みと、更新(MERGE)を練習するために、日々のデータが届く形を再現する必要がある。

## 決めたこと

- **リプレイ:** 日付 D ごとに、D に出来事(購入、承認、引き渡し、配達)があった注文を、D 時点で分かっている情報だけで出力する(スナップショットの形)。同じ注文が日をまたいで何度も出るので、Silver では MERGE が必要になる。
- **置き方:** `raw/olist/orders/ingest_date=YYYY-MM-DD/orders_YYYYMMDD.parquet`。1日1ファイルの Parquet。`ingest_date` はリプレイ上の日付で、実行した日ではない。
- **簡略化:** 日時の型(`timestamp`、UTC、タイムゾーンの印なし)は、Raw の段階で付ける。
- 監査カラム(`_ingested_at`、`_source_file`、`_batch_id`)を、ファイルに入れる。

## 理由

- スナップショットの形にすると、「同じ日付を再実行しても結果が変わらない(冪等)」を、実際に確かめられる。
- Parquet にすると、Athena が列の型を持ったまま読める。Bronze の外部テーブルが、変換なしでそのまま読める(ADR 0003)。
- 型を Raw の段階で付けると、Bronze と Silver で同じ型になり、Athena の `timestamp`(タイムゾーンなし)とも合う。

## あきらめたこと(弱い点)

- Raw が「元の姿そのまま」ではなくなる。実務では、Raw は元の文字列のまま持ち、型は Silver で付けることが多い。今回は、元の CSV(`data/olist/`)が手元に残るので、必要なら Raw を作り直せる。
- 日時として読めない値があると、型を付ける段階(`load_orders`)で実行全体が止まる。そのため、Python 側の検証で、読めない行を先に**隔離**する設計にした(ADR 0005)。
- 元データに無いキャンセルなどの日付は、最後に分かっている日付の翌日に、その状態になったことにして合成している。合成の印の列は持たない。必要になったら、フェーズ3で dbt を使ってルールから作る。
