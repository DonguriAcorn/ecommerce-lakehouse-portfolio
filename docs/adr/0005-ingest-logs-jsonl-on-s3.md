# ADR 0005: 取り込みのログは、S3 に JSON Lines で残す

- 日付: 2026-11-03(決めたのは 2026-10-31。詳細は docs/design/error-handling.md)
- 状態: 採用(Python の取り込みだけ。dbt の失敗は Airflow の運用で扱う)

## 状況

取り込みの Python(`ingestion/`)が問題を見つけたとき、どう止め、何を記録し、悪い行をどこに置くかを決める必要がある。

## 決めたこと

- ログは、`logs/ingest/olist/<テーブル>/run_date=YYYY-MM-DD/batch_id=<batch_id>/events.jsonl`(例: `<テーブル>` は `orders_events`) に、**JSON Lines**(1行 = 1つの出来事)で書く。項目は `ts`、`level`、`batch_id`、`table`、`stage`、`code`、`message` などに分ける。`message` は項目から組み立てる。
- 悪い行は、`quarantine/` に Parquet で置く。元の CSV の行を文字列のまま入れ、`_error_codes` などを足す。
- 止める(停止)か、悪い行だけを移す(隔離)かは、基準を決めた。元の CSV がない、必要な列が欠ける、隔離が全体の 1% を超える場合は停止する。それ以外は隔離して先に進める。
- 保存期間は、`logs/` が 90 日、`quarantine/` が 30 日。削除は S3 のライフサイクルで行う。

## 理由

- 項目に分けて持てば、Athena で「どの `code` が何件か」を集計できる。画面に出る文章だけでは、集計できない。
- S3 に置けば、Raw と同じ置き場所と権限(ingest ロール)で扱える。新しい基盤を足さずに済む。
- `run_date=` と `batch_id=` で分けておけば、1回の実行のログを、そのまま探せる。
- 隔離を元の文字列のままにすれば、直したあとに、同じ期間を再実行するだけで済む。

## あきらめたこと(弱い点)

- CloudWatch のようなログの専用基盤は使わない(このプロジェクトの対象外)。リアルタイムの検索やアラームは持てない。通知は Airflow の運用で決める。
- 実データ(orders)には、隔離に当たる行が0件のため、隔離の動きは本番のデータで確かめていない。フェーズ2の pytest で、悪い行を混ぜた小さな表を使って確かめる。
