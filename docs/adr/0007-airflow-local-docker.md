# ADR 0007: オーケストレーションは、ローカルの Docker で動かす Airflow にする

- 日付: 2026-11-03
- 状態: 採用(Airflow の土台は、フェーズ2でこれから作る)

## 状況

取り込みから Gold まで、日次の処理を順番に動かす仕組みが要る。要件は、冪等(同じ日付を再実行しても結果が変わらない)、バックフィル、リトライ、失敗通知である。

## 決めたこと

- Airflow を、**ローカルの Docker Compose** で動かす。
- 最初に作るのは、1日分の DAG で、冪等にする。
- AWS への認証は、管理者の長期の鍵をコンテナに入れない形にする(方式は ADR 0012。ロールの一時キーだけを渡す)。

## 理由

- Airflow と dbt は、GCP 上で使った経験がある。新しく覚えることを、AWS のサービスとデータの形に絞れる。
- コストの面で、AWS のマネージド型(MWAA)は課金がかなりかかる。ローカルで動かせば、常時動かす環境の料金がかからず、月額の上限(10 ドル)に合う。
- 取り込みの Python(`ingestion/`)や dbt など、外部のスクリプトを回す構成である。手元のコードをそのまま動かせる。
- 冪等、バックフィル、リトライ、失敗通知は、Airflow の標準の機能で扱える。

## あきらめたこと(弱い点)

- パソコンが止まれば、処理も止まる。本番の運用(常時稼働、監視、高可用性)は再現できない。
- AWS のマネージド型(MWAA)は使わない。課金が大きいため(見直すときは、料金を公式の文書で確かめる)。
- ローカルの Airflow から AWS に入る方式は、ADR 0012 で決めた(一時キーなので、使う前に発行し直す手間がある)。
