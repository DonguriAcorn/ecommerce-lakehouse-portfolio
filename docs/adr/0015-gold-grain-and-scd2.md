# ADR 0015: Gold は明細と注文の2つの事実テーブルにし、SCD2 は注文の購入日から SQL で作る

- 日付: 2026-11-14
- 状態: 採用(設計のみ。実装はフェーズ3の「Gold のスター型」と「SCD2」)
- 関係: ADR 0011(使うデータ)、docs/design/gold-design.md

## 状況

handoff の指標例は `fact_order_items`(明細)で、タスク名は `fact_orders`(注文)と、食い違っていた。売上とランキングは明細の `price + freight_value` から、リピート率と注文数は注文から数える。

customers は 2016-09-04 に1回しか届かないため、dbt snapshot では変化を見られない。一方、元データの中には変化がある(2注文以上の本人 2,997 人のうち、州が変わった人が 39 人、郵便番号が変わった人が 250 人)。

## 決めたこと

1. 事実テーブルは `fact_order_items`(明細1行)と `fact_orders`(注文1件)の2つ。
2. dim は `dim_customer`、`dim_product`、`dim_date`。sellers は、画面に出ないので作らない。
3. `dim_customer` は SCD2。dbt snapshot は使わず、注文の購入日時の順から、州と郵便番号の先頭5桁が変わった所で期間を区切り、`valid_from` / `valid_to` を SQL で作る。市の名前は本人の最新の値を持つ。
4. パイプライン健康状態の画面は、運用ログが元なので Gold の対象外にする。

## 理由

- 1つの粒度では、片方の指標が不自然になる。注文だけだとカテゴリ別の売上が出せない。明細だけだと、注文数とリピート率は count distinct になり、明細のない注文が消える。2つに分ければ、どちらも単純な集計で済む。
- 実データの変化を使えば、データを足さずに済み、業務の数字と一致する。デモ用に足したデータは、混ざると売上の突き合わせを崩す。

## 補足(実装時に決めたこと、2026-11-14)

- Gold は dbt の `table`(毎回、Silver から作り直す)で、保存の形式は Silver と同じ Iceberg。作り直すと Iceberg の版の履歴は引き継がれない。過去の数字を固定したくなったら、月次の KPI のスナップショット表を後から足す。
- 売上から外す状態は `canceled` と `unavailable`(`is_counted` 列)。`review_score` は、最後に答えたレビューの星。

## あきらめたこと(弱い点)

- 変化のある人が少ない(州で 39 人)。履歴のしくみを見せるには小さい。
- モデルが1つ増える。2つの事実テーブルの `order_amount` と `item_amount` の合計は、一致するテストで守る(フェーズ3の tests)。
- 履歴は購入日時からの推定で、本当の引っ越しの日ではない。
- dbt snapshot を使わないので、将来 customers が複数回届くようになっても、自動では履歴を足さない(そのときは作り直す)。
