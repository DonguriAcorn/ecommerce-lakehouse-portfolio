# ADR 0011: リプレイの対象を、BI の担当者から逆算した7つの表にする

- 日付: 2026-11-05
- 状態: 採用(実装はこれから。docs/tasks.md のフェーズ2「リプレイを、どのテーブルにも使える形にする」)
- レビュー: plan-critic による計6回のレビュー済み(2026-11-05)
- 関係: ADR 0010(orders のイベント単位の Raw)の「全9テーブル」を、この ADR で7テーブルに置き換える。仕様は docs/design/replay-tables.md

## 状況

orders だけ、simulator → ingestion → Raw → Bronze → Silver が完成している。コードは orders 専用で、テーブルを足すたびにコピーすると、検証の抜けや型のずれが散らばる。Olist には9つの CSV があるが、すべてを使う必要はない。実務では、画面を使う人と、その人が決めたいことから逆算して、集めるデータを決める。

## 決めたこと

- **担当者は3人+データ基盤。** 事業責任者(売上は伸びているか、どこが伸びたか)、営業(どの出品者を支えるか)、物流 CS(どこで遅れて、評価にどう効くか)。データ基盤は、パイプラインの健康状態を見る(handoff で決定済み)。
- **使う表は7つ。** orders、order_items、reviews、customers、sellers、products、product_category_name_translation。
- **payments と geolocation は使わない。** 3人の画面で使わないため。あとで要るとき(マーケの画面、細かい地図)は、registry に1行足せば載る形にしておく。
- **売上は、明細の `price + freight_value` で数える。** handoff §9 の例も直した。キャンセルと明細のない注文の扱いは、セマンティックレイヤー Lv1 で決める。
- **カテゴリ名は、英訳 → 元の名前(ポルトガル語)→ `unknown` の順で出す。** 行を落とさないので、売上の合計は変わらない。
- **表の種類と届く日:**
  - 出来事型: orders(ADR 0010 のまま)。
  - 追記型: order_items は親の注文の購入日に届く。reviews は max(客が答えた日, 親の購入日) に届く。行のない日も空のファイルを置く。
  - 一括型: customers、sellers、products、translation は、初日(2016-09-04)に全件が1回だけ届く。
- **テーブルごとの違いは、registry(仕様の表)に集める。** 名前、元の CSV、キー、列と型、種類、届く日の規則、`expected(table, date)`、PII の候補の印。受付の流れ(読む → 検証 → 型 → 監査カラム → Raw)は共通にする。
- **元の CSV との行数の照合は、このタスクではしない。** 「全テーブルの Bronze と Silver」のタスクで、キーの種類の数で照合する。

## 理由

- 画面から逆算すると、データを集める理由を1つずつ説明できる。ポートフォリオで「なぜこの表か」に答えられる。
- 売上を明細で数えると、カテゴリ別・出品者別の内訳と合計が同じ表から出る。支払いは注文の単位で、明細に分けられない。
- 測定(2026-11-05、元の CSV): カテゴリが空の商品は 610 件で、売上の約 1.31%。英訳のないカテゴリは2つ(`pc_gamer`、`portateis_cozinha_e_preparadores_de_alimentos`)の 13 商品で、売上の約 0.04%。落とすと、空のほうはランキングで気づきにくい量になる。
- reviews の `review_creation_date` はアンケートを客に送った日で、星と本文は客が答えた日時(`review_answer_timestamp`)にできる。送ってから答えるまで、中央値 1 日、最大 518 日かかる。送った日に届けると、答える前に評価が見えてしまうため、答えた日にした(2026-11-05。計画の max(作成日, 購入日) から変えた)。作成日が購入日より前の行が 64 件あるので、max を取って、親の注文より前に届かないようにする。出来事(送った・答えた)には分けない。送っただけの行は、どの画面でも使わないため。答えた日が最後の注文より後の行が 9 件あるので、reviews だけ期間の最後を 2018-10-29 にする(ほかの表は 2018-10-18 のまま)。
- 一括型にすると、日付の意味がない表(マスタ)に、作った日付を付けずに済む。

## あきらめたこと(弱い点)

- 支払い方法(分割払い、ボレート)と、緯度経度の地図は分析できない。AI アナリストの評価セットにも、その質問は入れない。
- customers を初日に全件届けるので、「新しい顧客が日々増える」様子は Raw にない。顧客の住所の履歴(SCD2)は、Silver で customers を orders と結び、購入日時を有効日にして作る(住所が変わった人は 252 人)。
- 追記型の2つの表は 775〜786 日分のファイルになり、小さなファイルが増える。意図した割り切りとし、Iceberg 側の整理は Airflow の運用で扱う。
- 遅延の再現は orders だけ。子の表(order_items、reviews)には遅延を入れない。
