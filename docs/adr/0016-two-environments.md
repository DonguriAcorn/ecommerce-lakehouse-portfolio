# ADR 0016: 環境は dev と prod の2つにする(test は作らない)

- 日付: 2026-11-25(決定は 2026-11-14)
- 状態: 採用
- 関係: [ADR 0001](0001-environment-separation.md)(環境の数を置き換える。「名前で分ける」は有効)、tasks.md のフェーズ4

## 状況

ADR 0001 は、dev / test / prod の3環境を、同じ AWS アカウントの中で名前で分けると決めた。しかし、アカウントを分けない限り、test は名前が違うだけで、権限の境界もデータの境界も dev と変わらない。月額の上限(10 ドル)の中で、3環境ぶんのデータと実行を持つ費用も重い。

## 決めたこと

1. 環境は dev と prod の2つにする。test は作らない。
2. 0001 の「アカウントを分けず、名前で分ける」「定義は1つのモジュールにまとめ、`env` を渡して呼び分ける」は、そのまま有効にする。置き換えるのは、環境の数(3 → 2)だけである。
3. test が担っていた検証は、次の3つに集める。
   - PR のチェック: ruff、pytest、`terraform plan`、`ecom_ci` での `dbt build`。`ecom_ci` は1つだけで、並行する PR は禁止し、固定の小さなデータで流す。
   - prod への手動承認: main へのマージのあと、承認画面で plan の要約を見て承認する。保存した plan だけを apply する。
   - ブランチ保護: PR チェックを通らない変更は main に入れない。
4. dev への自動デプロイはしない。dev は、手元の portfolio-admin で動かす。
5. prod のデータは全期間を入れる。

## 理由

- 同じアカウントの test は、名前の違いしかなく、本物の隔離にならない。隔離にならないものに費用と手間をかけても、守る力は増えない。
- 「本番に出す前に、実物に近い所で確かめる」という test の目的は、PR の `ecom_ci` と、人が plan を読む承認で、小さく満たせる。
- 環境が減ると、ロールとプロファイルも減る(deployer は prod 専用の1つ)。

## あきらめたこと(弱い点)

- 本物の隔離がない。dev と prod は同じアカウントにあり、IAM の誤りや誤操作が、環境をまたいで効く可能性が残る。
- `ecom_ci` は dev の Bronze を読む。dev のデータが壊れると、CI の結果も影響を受ける。
- 人が承認画面の plan を読み間違えると、prod に誤った変更が入る。承認の質が、最後の守りになる。
- test がないので、prod に近い大きさのデータでの総合的な確認は、prod へ出す前にはできない。

## 将来の乗り換え

規模や利用者が増えたら、アカウントを環境ごとに分け、staging を足す。モジュールは `env` を渡す形のままなので、provider だけを環境ごとに変えて移れる(0001 と同じ)。
