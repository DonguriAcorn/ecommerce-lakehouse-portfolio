## 2. プロジェクト概要

- **目的**: 実務に近い構成のデータ基盤を一人で作り、設計判断まで説明できるポートフォリオにする。
- **ゴール**: 公開URLで触れる Streamlit アプリ(ダッシュボード + AIアナリスト)と、GitHub 上の再現可能なコード・ドキュメント一式。
- **ユーザーの状況**: データ分析の実務経験があり、データエンジニアとして学習中。別プロジェクトで GCP 上の Airflow + dbt の経験があり、AWS のデータエンジニア資格(DEA-C01)も勉強している。
- **進め方の希望**: できるだけ無料で構築する。セマンティックレイヤーを含め初めての内容が多いので、作りながら学び、各ステップのコードを一つずつ確認しながら進めたい。
- **対話のルール**: 日本語で回答する。コードは1つずつ確認しながら進め、1行ずつ丁寧に説明する(初めての内容が多いため。一行要約よりこちらを優先する)。手順を説明するときは、すべてのステップでコピー&ペーストできるコードを付ける。

## 3. 確定した方針

| 項目 | 決定 |
| --- | --- |
| データレイク | S3(同じ AWS アカウントの中で、環境(dev / test / prod)ごとに1バケットにし、中を raw/、iceberg/、athena-results/ のプレフィックスで分ける。権限は処理用の IAM ロールで分け、環境ごとのアカウント分離は ADR に書く) |
| テーブル形式・カタログ | Iceberg + Glue Data Catalog |
| 変換・クエリ | dbt-athena + Athena(Silver / Gold を Iceberg で作成、MERGE を使う) |
| オーケストレーション | Airflow(ローカル Docker Compose) |
| IaC | Terraform |
| CI/CD | GitHub Actions(OIDC で AWS に接続) |
| 環境 | dev / test / prod の3環境 |
| アプリ | Streamlit Community Cloud。BI ツールは併用しない |
| AI | LLM API(閲覧者のキー入力か回数制限で運用) |
| ネットワーク | VPC などの設計は入れない。S3 の TLS 強制のみ入れる |
| Databricks | 使わない(Free Edition は S3 の読み取りに制限がある可能性があり、無料方針にも合わないため) |
| コスト方針 | 無料に近い範囲。AWS Budgets と Athena の workgroup 上限で守る |

## 4. 全体構成

```
Olist データ + リプレイスクリプト
  → S3 Raw (Bronze: Parquet・日付パーティション)
  → dbt + Athena (MERGE・テスト・指標定義)
  → S3 Iceberg (Silver / Gold、Glue Catalog で管理)
  → Gold を Parquet に export (公開用の小さな集計)
  → Streamlit アプリ (ダッシュボード + AIアナリスト、DuckDB で Parquet を読む)

Airflow が全工程を制御し、GitHub Actions + Terraform が CI/CD と環境(dev / test / prod)を担う。
```

公開アプリには AWS の認証情報を持たせない。Gold の集計結果を Parquet にして渡し、アプリは DuckDB で読む。

## 5. データ(仮置き)

- **Olist Brazilian E-Commerce**(Kaggle)を使う想定。注文ステータスの変化を日付順にリプレイして、日次の増分・更新・キャンセル・遅延到着を再現する。
- ライセンスは非商用の条件付きの可能性があるため、公式ページで条件を確認すること。
- 必要に応じて、為替などの無料 API の取り込みを足して、ファイル取り込みと API 取り込みの両方を見せる案がある。

## 6. 要件

### 機能要件

- **パイプライン**: 日次でリプレイし、Silver で重複排除と最新化(MERGE)を行う。Gold はスター型(`fact_orders`、`dim_customer`、`dim_product`、`dim_date`)。同じ日付を再実行しても結果が変わらない(冪等)。過去日付のバックフィルもできる。
- **環境とデプロイ**: Terraform の変数で3環境を切り替える。PR 時に lint、テスト、`terraform plan`、一時スキーマでの `dbt build` を実行する。main へのマージで test に自動デプロイし、prod は手動承認(GitHub Environments)にする。
- **データ品質・運用**: dbt tests、鮮度チェック、データコントラクト、ジョブ失敗時の通知、Iceberg の定期メンテナンスを入れる。
- **アプリ**: ダッシュボード(売上 KPI、期間比較、リピート率、商品ランキング、パイプライン健康状態)と、AIアナリスト(質問 → SQL 生成 → 検証 → 実行 → 表・グラフ・要約)。

### 非機能要件

- **コスト**: 月額の上限を決め、AWS Budgets、Athena の workgroup スキャン上限、S3 ライフサイクルで守る。
- **セキュリティ**: キーをリポジトリに置かない(OIDC、Streamlit Secrets、SSM)。IAM は最小権限、S3 はパブリックアクセスをブロックして暗号化する。AI が生成する SQL は SELECT のみ、Gold のみ、`LIMIT` 付き、PII カラムは除外する。
- **再現性**: README の手順だけで第三者が環境を立ち上げられる。
- **説明可能性**: 設計判断を ADR に残し、dbt docs を公開する。

## 7. スコープ

方針: 「必須」と「推奨」はすべて含める。「余裕があれば」は今回は対象外。

### 含める要素

| 領域 | 必須 | 推奨 |
| --- | --- | --- |
| データ基盤 | S3 + Iceberg + Glue Catalog、Olist のリプレイ、Airflow(冪等・バックフィル・リトライ・失敗通知)、Silver の MERGE、Gold のスター型、SCD Type 2、Gold の Parquet export | Iceberg の運用(compaction・スナップショット削除)、スキーマ進化のデモ、Raw・Silver の監査カラム(取り込み日時・元ファイル名・バッチ ID) |
| 環境・CI/CD | Terraform、dev / test / prod、GitHub Actions + OIDC、PR チェック、prod の手動承認 | Slim CI(`state:modified+`)、`ruff` / `sqlfluff` / `pre-commit`、`pytest` |
| データ品質 | dbt tests、鮮度チェック | データコントラクト、dbt docs の公開(軽量なデータカタログとして位置づける)、dbt の meta / tags による管理情報(オーナー・PII フラグ・更新頻度)と用語集 |
| セキュリティ・コスト | シークレット管理、IAM の最小権限と S3 の保護、コスト上限 | PII のハッシュ化、月次コストの記載 |
| 運用 | なし | パイプライン健康状態ページ、Runbook |
| アプリ・AI | ダッシュボード、セマンティックレイヤー Lv1・Lv2、ガードレール、悪用対策 | AIアナリスト、評価セット、質問ログ、PII フラグとガードレールの連携 |
| ドキュメント | README | ADR、「やらないこと」の明記 |

### メタデータ管理(推奨として追加)

- **監査カラム(フェーズ2)**: Raw と Silver のテーブルに、`_ingested_at`(取り込み日時)、`_source_file`(元のファイル名)、`_batch_id`(実行の識別子)を入れる。不具合の調査や再実行の確認に使う。
- **管理情報(フェーズ3)**: dbt の `meta` と `tags` で、各モデル・カラムに `owner`、`pii`、`update_frequency` を持たせる。用語集(「GMV」「リピート率」などの定義)を1ページ用意する。内容は dbt docs に表示される。
- **PII フラグとガードレールの連携(フェーズ6)**: `pii: true` のカラムを、AI アナリストが見られないカラムの一覧として自動で使う。除外リストを別に手書きしないので、定義のずれが起きない。

### 対象外(バックログ)

- セマンティックレイヤー Lv3(MetricFlow など)
- OpenLineage
- IaC のセキュリティスキャン(`checkov` / `tfsec`)
- 障害注入のデモ
- 複数ステップの分析(AIアナリストの高度化)
- 専用データカタログ(OpenMetadata / DataHub など)。人がデータを探すためのカタログは dbt docs で代用し、専用ツールは規模が大きくなった場合の選択肢として ADR に書く
- CloudWatch のアラームなど(Athena のスキャン量の監視)。今回は入れず、後半で必要になったら追加する

### 入れないと決めたもの

ストリーミング(Kinesis / Kafka)、Kubernetes など複雑なインフラ、機械学習モデルの構築、BI ツールの併用、ネットワーク設計。README の「やらないこと」に、理由つきで明記する。

### フェーズ8: Snowflake 連携(v1.0 以降の拡張)

- **目的**: 同じ S3 上の Iceberg テーブルを別エンジン(Snowflake)から読み、Iceberg の相互運用を実際に示す。
- **方針**: 追加するエンジンは Snowflake の1つだけ。Databricks と BigQuery は使わない。Snowflake からは読み取り専用とし、書き込みは Athena + dbt のみで行う。
- **無料での進め方**: Snowflake には永続の無料プランがなく、30日のトライアルのみ。サインアップはフェーズ7の完了後に行い、30日以内にこのフェーズを終える。トライアル終了後はデータが削除されるため、成果は README のスクリーンショットと ADR に残す。
- **内容**: (1) Glue カタログ連携で Iceberg テーブルを Snowflake から読む(設定は着手時に公式ドキュメントで確認)。(2) 同じ集計 SQL を Athena と Snowflake で実行し、結果の一致を確認するテストを作る。(3) 実行時間・課金の仕組み・使い勝手の比較を ADR にまとめる。
- **完了の目安**: 同じ SQL が両エンジンで同じ結果になり、比較表が README にある。
- **進め方のルール**: 1つずつ確認しながら進める方式は、このフェーズでも変えない。

### 社内展開時の構成(ADR・実施未定)

- **位置づけ**: 実施するかどうかは未定。実施する場合は、フェーズ7のドキュメント作業として、設計だけを ADR に書く(実装はしない)。
- **前提**: アプリの利用者は、社内ユーザーのような位置づけを想定している。公開アプリ + Parquet + DuckDB の構成はポートフォリオ用の工夫であり、実運用の構成ではない。
- **書く内容**: ホスティング(社内で管理するコンテナ基盤を、社内ネットワークの内側に置く)、認証(SSO)、認可(部署・役割ごとの行・列の制限)、データ接続(読み取り専用のロールでデータ基盤に直接つなぎ、クエリ量の上限を設ける)、LLM(会社が承認した提供形態、データの外部送信ルール、利用量の上限)、機密データ(PII のマスキング、AI に見せる列の制御)、ログ・監査(誰が何を質問し、どの SQL が動いたか)、運用(障害通知、問い合わせ窓口、変更管理)、導入の進め方(少人数・限定データでの試験運用、セキュリティ部門との確認、評価セットで継続的に精度を測る)。
- **補足(既存のスコープとの関係)**: 最小権限、PII の扱い、ガードレール、質問ログは、すでにスコープに入っており、この構成の土台になる。
- **補足(DuckDB の位置づけ)**: DuckDB はアプリ側だけで使う。Parquet を直接 SQL で読め、サーバーが要らず無料で、公開アプリに AWS の認証情報を持たせずに済むため。変換の本線は Athena + dbt のままにする。

## 9. セマンティックレイヤー方針

セマンティックレイヤーは、**「売上」「リピート率」などの意味と計算式を1か所で定義し、人にも AI にも同じ解釈で使わせる仕組み**。ユーザーは初めてなので、次の3段階で、作りながら学べるように支援する。

- **Lv1**: dbt の YAML にテーブルとカラムの説明を書く(フェーズ3)。
- **Lv2**: 自前の YAML で指標を定義し、ダッシュボードと AI が同じ定義を読む(フェーズ5)。
- **Lv3**: MetricFlow など専用の仕組み(今回は対象外)。

Lv2 のイメージ:

```yaml
# semantic/metrics.yml
metrics:
  - name: gmv
    label: 総流通額
    description: 支払済みの注文金額の合計(キャンセル除く)
    table: gold.fact_orders
    expression: SUM(payment_value)
    filter: order_status != 'canceled'
    time_dimension: order_date
```

## 10. AIアナリストの設計方針

- **流れ**: 質問 → LLM が SQL を生成 → 検証 → DuckDB で実行 → 表・グラフ・要約を返す。
- **入力**: Gold のスキーマ、dbt のカラム説明、`semantic/metrics.yml` の指標定義を LLM に渡す。
- **ガードレール**: SELECT のみ、Gold のみ、`LIMIT` の強制、PII カラムの除外(除外するカラムは、メタデータの PII フラグから自動で決める)。構文チェックには `sqlglot` を使う。
- **評価**: 20〜30問の「質問 → 期待する結果」を用意し、CI で正答率を測る。
- **ログ**: 質問、生成した SQL、実行時間、エラーを Iceberg に貯める。
- **公開時の悪用対策**: 閲覧者が自分の API キーを入力するか、1日あたりの回数に上限を設ける。作者のキーを公開アプリに載せたままにしない。

## 11. 進め方のルール

手順を説明するときは、コピー&ペーストできるコードを各ステップに付けること。
